¿Cómo está hecho?

Documentación académica del proyecto: arquitectura, decisiones y evidencia

Aquí está todo el proyecto explicado: cómo el escritorio y las dos webs hablan el mismo idioma, qué decisiones tomé y cómo comprobarlo. Bienvenido al código.
El código fuente completo está en GitHubgithub.com/HLSC0105/penguin-english-adventure

1. El mapa del código: Python ↔ Web

datos/ (vocabulario · trivia · memoria · pipo · niveles)

El único origen de verdad del contenido: 309 palabras en 20 categorías, 107 preguntas de trivia, 16 parejas y los mensajes de Pipo, cada entrada etiquetada con su nivel CEFR. El escritorio importa estos módulos directo; las dos webs los RECIBEN: scripts/astro_exportar.py (y web_exportar.py para la vanilla) emiten los datos desde el Python real, así el contenido se edita UNA vez y todas las versiones quedan sincronizadas.

Web → 00-datos.js (vanilla) · src/data/*.json (Astro)

juegos/ (trivia · completar · ordenar · memoria)

Lógica pura sin interfaz: repartir preguntas sin repetir, crear el hueco (con la regla B1 de no ocultar la letra inicial), desordenar letras garantizando un anagrama distinto del original, armar el tablero de parejas palabra-imagen y validar intentos. Las mismas funciones sirven a tres front-end distintos: Tkinter, la web vanilla y las islands de Astro.

Web → 04-juegos.js (vanilla) · src/lib/juegos.ts (Astro)

utilidades/puntuacion.py

Los acumuladores del negocio: +10 por acierto (una llamada por intento), +20 de bonificación por terminar (ya sumada ANTES de entrar al resultado para que el repinte del tema no la duplique), lista de actividades completadas y porcentaje de aciertos.

Web → 02-estado.js (vanilla) · src/lib/estado.ts (Astro)

utilidades/sonidos.py

pygame.mixer con WAV locales y degradación amable: si el mixer no arranca, el juego sigue con el aviso «Sin sonido». Las webs logran la misma promesa con un POOL de 3 nodos de Audio por efecto (un efecto que aún suena no se corta) y reconstrucción del nodo si queda envenenado tras repetir muchas veces.

Web → 03-sonidos.js (vanilla) · src/lib/sonidos.ts (Astro)

utilidades/rutas.py

Resolución de rutas de recursos empaquetados (PyInstaller _MEIPASS o el repo). En la web vanilla es trivial: rutas RELATIVAS a index.html; en Astro el reto es el base path de GitHub Pages — todo pasa por src/lib/rutas.ts con import.meta.env.BASE_URL.

Web → rutas relativas (vanilla) · src/lib/rutas.ts (Astro)

interfaz/componentes.py

El cascarón compartido: encabezado persistente con HUD (puntos, aciertos, nivel), título animado, Pipo y su burbuja, tokens de tema (20 llaves exactas: TEMA_OSCURO/TEMA_CLARO), botones, tarjetas, barra de progreso y repintar_pantalla. Las webs agregan lo que CSS regala: sistema de elevación --elev-1/2/3 y backdrops-blur.

Web → 05-componentes.js (vanilla) · Layout + components/*.astro (Astro)

interfaz/animaciones.py

Tkinter no tiene motor de tween: la skill académica es encadenar widget.after(ms, paso) con interpolación lineal y ease_out_cubic (t=1-(1-t)³). TODAS las animaciones del escritorio existen en las webs: animar_aparicion_titulo, pulsar_widget, animar_barra, resal_burbuja_pipo, fundir_fondo. Astro añade lo que el navegador tiene de fábrica: View Transitions entre rutas y cascada por hijos.

Web → keyframes en estilos.css (ambas webs)

interfaz/lienzo_pygame.py

El volteo 2.5D de las cartas y el confeti de la celebración, dibujados con pygame y proyectados por cos θ al plano (el «canto» de la carta al girar). Las webs logran el mismo giro con perspective + rotateY de CSS — sin canvas. El confeti corre en modo continuo hasta navegar (reciclaje de partículas en un requestAnimationFrame que muere solo al desenlazarse el canvas).

Web → cartas .memoria-carta + confeti canvas

interfaz/*.py (pantallas)

Nueve pantallas con la misma forma: inicio con validación, menú con selector CEFR y fichas de actividades, vocabulario paginado 4×página, trivia/completar/ordenar con feedback coloreado y explicación, memoria con contadores, resultado con el mensaje de Pipo por umbral (100%→perfecto, ≥60%→felicitaciones, <60%→ánimo) y la documentación.

Web → pantallas/*.js (vanilla) · src/pages/*.astro + islands (Astro)

4. Conceptos académicos clave

Bucle de eventos

El juego no espera bloqueando: reacciona. En Tk, el mainloop recibe eventos; en la web, el bucle del navegador dispara los callbacks de clic y los rAF de animación. Un algoritmo PSeInt se convierte en este modelo: escribir → enter → pantalla nueva.

Estado en parámetros

Ninguna pantalla guarda su propio estado: el índice de pregunta, los aciertos y la palabra viajan como ARGUMENTOS (o en la sesión de la pestaña). Así el «Volver» y el redibujado nunca se desincronizan del progreso.

CEFR acumulativo

A2 incluye A1; B1 incluye los dos. El filtro compara índices en la tupla ordenada y EXPORTA su efecto al reto: rondas (6/8/10), parejas (4/6/8), preguntas (8/10/12), espera del flip (1100/900/650 ms) y si se oculta la letra inicial (sí/sí/no).

Degradación amable

Sin sonido → pool/reconstrucción y aviso visible; sin imagen → círculo con la inicial; sin red → todo es local. El juego SIEMPRE se juega: cada punto de falla tiene camino de respaldo.

Movimiento reducido

prefers-reduced-motion apaga cascadas, reparto y confeti, y mata la animation-delay (los hijos no pueden quedar invisibles esperando su turno). La elevación queda estática.

Front-millares: herencia y composición

La web no reescribe el mundo de Tk: HEREDA sus 20 tokens y constantes y agrega capas propias (elevación, cascada, pool). «Refinement sin redesign»: el mismo producto, otro motor.

5. La versión Astro: cómo y por qué

Del SPA al MPA con transiciones

La versión vanilla es UN documento con pantallas pintadas por JS (navegar() guarda la pantalla para el repintado). Astro invierte el modelo: cada pantalla es una RUTA con HTML pre-renderizado; al navegar el navegador hace la transición de vista (::view-transition-old/new) — el vaivén premium sin JS de control.

Cero JavaScript en las páginas estáticas

Menú, ayuda, intro, documentación y resultado son HTML puro + CSS: el envío de JS es solo el de las islands (4 juegos + hud/tema/splash). La vanilla carga toda la app en cada visita; Astro envía cada pieza SOLO donde vive.

Datos en build, no en runtime

La vanilla emite 00-datos.js y lo lee el navegador; Astro importa src/data/*.json en el frontmatter (build): el contenido queda incrustado en el HTML, tipado con los esquemas, y no hay fetch ni parseo en el cliente.

Imágenes optimizadas por pipeline

astro:assets convierte los OpenMoji 618px a webp con dimensiones fijas: menos peso, cero layout shift, nitidez en pantallas de alta densidad. La vanilla servía PNG tal cual.

Bun como gestor

Todo el ciclo corre con bun (install/dev/build/preview): el mismo proyecto enseña npm-compatible y la alternativa moderna. Los comandos del README son bun primero, npm como fallback.

6. Decisiones de diseño y trade-offs

Un solo origen de verdad

El contenido vive en Python y las dos webs lo reciben generado (web_exportar.py / astro_exportar.py). Cambiar una palabra no toca ninguna web: se regenera y ambas quedan al día.

Sin build (vanilla) / build mínimo (Astro)

La vanilla existe PRECISAMENTE para enseñar cómo funciona una web sin herramientas; Astro añade el build como la evolución natural — y desplegar.sh permite PUBLICAR cualquiera de las dos.

Sesión por pestaña (sessionStorage)

Los puntos sobreviven recargas dentro de la pestaña y se borran al cerrarla: práctica conservada sin dejar datos en la máquina de clase.

Pool de audio + caché de media

Dos problemas de sesiones largas (sonidos mudos tras ráfagas; imágenes degradadas tras 60+ navegaciones) se resolvieron con retención: pool de 3 nodos por efecto y caché de imágenes decodificadas.

El mismo algoritmo dos veces

juegos.ts/.js espejan juegos/*.py a propósito: permite aprender los dos paradigmas (procedural Tk y declarativo DOM) sin un puente de compilación.

Tokens sobre magia

Cada color/ritmo sale de una variable CSS documentada. Ningún color hardcodeado en pantallas: el tema claro/oscuro se resuelve sin reescribir componentes — igual en las dos webs.

8. Cómo reproducir y distribuir

Jugar sin nada (vanilla)

Doble clic en web/index.html (o el zip). No necesita Python, servidor, internet ni instalación — es la versión de pendrive.

Jugar la versión Astro (la publicada)

Esta misma página: GitHub Pages la sirve desde la rama gh-pages con el build de Astro.

Regenerar contenido

source .venv/bin/activate && python scripts/astro_exportar.py (Astro) o python scripts/web_exportar.py (vanilla) tras editar los datos.

Refrescar imágenes

python scripts/descargar_openmoji.py --catalogo --tamano 618

Correr las suites

tests_web/: bun/npm i + npm test (vanilla) o npm test:astro (Astro) — corren por file:///preview con la red externa bloqueada.

Desplegar una u otra

scripts/desplegar.sh astro (por defecto) o scripts/desplegar.sh vanilla — sincroniza la versión elegida a la rama gh-pages (misma URL, contenido distinto).

Probar el escritorio

python -m penguin_english (venv con pygame) · tests: python -m unittest discover.
